## 为什么拆它

PCL2（Plain Craft Launcher 2）是国内用得最多的 MC 启动器之一。它只有一个 exe，6 MB，没有安装包、没有依赖目录，却能完成版本下载、登录、联机、资源搜索、自动更新这一整套功能。

我关心三个问题：

1. 单文件是怎么把十几个依赖藏进去的
2. 这些功能在代码里是怎么组织的
3. 一个要读账号 token、又要以管理员权限运行的东西，有没有藏着不该有的东西

下面按实际分析的顺序写，重点是“每一步为什么这么查”，不是结论堆砌。

---

## 第一步：先确认它是什么，别急着反编译

拿到 exe，先看元数据，不碰代码：

```text
PE32 (x86), GUI 子系统
CLR 数据目录存在，运行时版本 v4.0.30319
→ .NET Framework 4.x，不是 .NET Core 单文件
```

再看引用表：`PresentationFramework`、`System.Xaml`、`WindowsBase` —— WPF。到这里可以确定是托管程序，直接上反编译器即可，不需要 IDA。

**关键判断**：有没有混淆。看类型名就知道——`PCL.ModMain`、`PCL.ModLaunch`、`PCL.McLoginType` 全部可读，说明没有改名/控制流混淆，反编译出来就是可读源码。

还有一个意外收获：日志字符串里保留了编译机的绝对路径（`E:\Projects\PCL\本体代码\...`），直接暴露了项目结构。这不是手滑，是 `[CallerFilePath]` 的副作用——日志 API 为了显示来源文件，把编译期路径固化了。全文 1179 处，覆盖 95 个源文件名，等于免费给了模块地图。

---

## 第二步：单文件的依赖藏哪了

**思路**：引用表里有一堆程序集（MeloongCore、PCLCS、NAudio、Newtonsoft.Json……），但目录里只有 exe。要么是 ILMerge 合并，要么是资源嵌入 + 运行时加载。

先排除 ILMerge：反编译主程序只有 163 个类型，全部在 `PCL` 命名空间下，没有第三方类型混进来。所以依赖不在这一个程序集里。

接着查加载路径：在 `Application` 的静态构造器里找到 `AppDomain.CurrentDomain.AssemblyResolve`，逻辑是“按前缀匹配资源名 → 从 `PCL.Resources.resources` 取 byte[] → `Assembly.Load`”。

于是直接读资源表，拿到 18 项：

```text
PCLCS / MeloongCore / MeloongCore.Wpf / Newtonsoft.Json
NAudio / Ookii.Dialogs.Wpf / CacheCow.* / Imazen.WebP
libwebp64 / System.Net.Http.Formatting / ThrottleDebounce
Custom（主页模板）/ Help（帮助文档 zip）/ ForgeInstaller / Transformer
```

全部落盘，逐个反编译。这一步之后，整个程序就没有黑盒了。

小细节：加载 `Imazen.WebP` 时会顺带释放原生 `libwebp.dll`，并调用 `SetDllDirectory` 把它所在目录加进 DLL 搜索路径。

---

## 第三步：反编译引擎的选型

之前用的 ILSpy 8.2 有点老。机器上装了 ILSpy 11.1，但直接引用它的 DLL 会报错：

```text
System.Runtime, Version=10.0.0.0 高于所引用的 8.0.0.0
```

原因：GUI 版是 net10 编译的，本机只有 .NET 8 SDK。**思路**：不装 SDK，直接用 NuGet 包。`ICSharpCode.Decompiler 11.1.0.9782` 带 netstandard 目标，net8 项目可以直接引用。

写了个几十行的驱动：读 PE → `CSharpDecompiler` → 按类型逐个输出 `.cs`。踩的坑不多但典型：

- 依赖解析失败会直接抛异常，要给它一个搜索目录（原程序集所在目录）
- 编译器生成类型（如匿名类型）不算业务代码，跳过
- 类型名里带 `<>`，不能直接当文件名

最终产物：主程序 163 个文件 3.4 MB，加上 PCLCS、MeloongCore 两个库。全部可读，无混淆。

---

## 第四步：从类型列表重建模块地图

**思路**：不按命名猜，按“谁大、谁被谁调用”排。

| 模块 | 职责 |
|---|---|
| `ModLaunch` 系列 | 登录、启动参数、JVM 参数、启动管线 |
| `ModMinecraft` | 实例扫描、版本解析、隔离目录 |
| `ModDownload` / `ModDownloadLib` | 版本清单、加载器元数据、下载引擎 |
| `ModNet` | HTTP 层、重试、缓存、源切换 |
| `ModSecret` | 主题、更新、服务器公告、捐赠相关 |
| `ModModpack` / `ModLoader` | 整合包安装、任务调度 |
| `ResourceSearcher` / `ResourceProject` | CurseForge / Modrinth 搜索 |
| `Page*` / `My*` | 页面与自绘控件 |

日志字符串里泄露的目录统计也能交叉验证：`Modules` 531 处、`Pages` 434 处、`Controls` 68 处——和上面的分布一致。

---

## 第五步：顺着主流程读，而不是按文件读

启动器的主线只有三条：启动、登录、下载。按代码执行顺序读，比按文件读高效得多。

**启动**：入口 → 单实例互斥 → .NET 4.8 检查 → 主窗口。

**登录**：四种类型，微软 OAuth（device code → XBL → XSTS → Minecraft）、统一通行证、authlib、离线。token 全部落在设置项里。

**启动游戏**：固定十步的管线，每步是一个带权重的 `LoaderTask`：

```text
获取 Java → 登录 → 补全文件 → 生成参数 → 解压 Natives
→ 预启动 → 执行自定义命令 → 启动进程 → 等窗口 → 收尾
```

这个结构解释了很多行为：为什么补全文件失败时游戏起不来、为什么自定义命令在游戏进程之前执行、为什么进度条权重是那些数字。

---

## 第六步：安全审计，先列能力面再排除

**思路**：不要漫无目的地搜关键词，先定义“一个程序能作恶的方式”，再逐项验证。

| 能力面 | 检查方法 | 结论 |
|---|---|---|
| 动态加载代码 | 搜 `Assembly.Load` / `Reflection.Emit` / `CSharpCodeProvider` | 只有一处，加载自身嵌入资源 |
| 执行外部程序 | 枚举所有 `Process.Start` | Java、cmd（用户自定义命令）、联机模块、自更新 |
| 外联 | 提取所有 URL | Mojang、微软、BMCLAPI、CurseForge/Modrinth、meloong、腾讯云 |
| 持久化 | 搜 Run 键、启动目录、计划任务、服务 | 无 |
| 敏感文件 | 搜浏览器数据、SSH、文档目录 | 无 |
| 键盘/截屏 | 搜对应 API | 无（只有窗口拖拽的按键检测） |

后门结论：**没有**。但“没后门”不等于“没问题”，审计过程里发现了几类设计层面的风险，其中最有意思的是一处提权面。

---

## 第七步：提权那条链是怎么被找出来的

这条链不是搜出来的，是顺着“谁以什么权限执行什么”推出来的。推理过程如下。

### 问题一：哪些东西会以 PCL 的权限执行？

PCL 的清单是 `asInvoker`，默认不提权。但它有多处会主动要管理员：

- 内存优化功能
- 显卡首选项设置
- 更新失败时的提示

也就是说，“以管理员运行的 PCL”是常见状态，不是异常状态。

在这个前提下枚举 `Process.Start` 的调用点，发现一类输入很特别：**自定义启动命令**。它是 PCL 的正常功能，用户可以在设置里写任意命令，启动游戏时由启动器执行。

### 问题二：这个输入谁能写？

追设置项的存储位置：

- 一部分存注册表 HKCU
- 一部分存 PCL 目录下的 `Setup.ini`
- 一部分存每个实例目录下的独立 `Setup.ini`

三者都是**当前用户可写**的。而同用户的低权限进程（比如浏览器里跑出来的恶意脚本）恰好也以这个用户身份运行。

### 问题三：执行前有没有校验？

没有。读出来直接拼进 `cmd.exe /c`，没有签名、没有完整性检查、没有来源确认。

### 把三点连起来

```text
管理员 PCL + 用户可写的 ini + 无校验的 cmd /c
→ 低权限进程改配置
→ 用户下次启动游戏
→ 命令以高完整性运行
```

这就是一个标准的 UAC 绕过：不需要再弹一次 UAC，因为提权发生在用户自己启动 PCL 的那一刻。

### 怎么验证

验证思路是“不要只信代码，要拿到令牌证据”：

1. 用高完整性环境生成一份进程组令牌清单（`whoami /groups`），看强制完整性级别
2. 用一个必须管理员权限的自检型程序做对照：中完整性启动会自己弹 UAC，高完整性启动不会
3. 两次实验都拿到 `S-1-16-12288`（High Mandatory Level）

对照组很关键：它排除了“只是把程序拉起来了”这种误判，证明继承的确实是高完整性令牌。

这条链本身不复杂，值得写的是它的**类别**：高完整性程序信任用户可写输入。判据只有三条：

1. 以高完整性运行
2. 从用户可写位置读配置/脚本/插件路径
3. 读完直接执行或加载，没有校验

三条全中就能打。同类落点还有插件目录、更新器、解释器参数、DLL 搜索路径。这也是为什么审计时要先画“能力面”，再追“输入来源”——单个函数看不出问题，连起来才成立。

> 本文只讨论思路与类别，不提供利用代码与复现步骤。

## 顺带发现的几处代码

审计之外，代码里还有些值得一提的东西。

**启动按钮会逃跑**：4 月 1 日限定的彩蛋。鼠标靠近时按钮会按斥力向量位移，边缘还会传送；鼠标静止 320 帧后它会主动逃离。变量名 `AprilDifficultiedDistance`，作者自己造的语法错误。点中后解锁隐藏主题。

**今日人品是算出来的**：`hash(日期, 年份, 设备码)` 取模，跟运气无关，纯确定性。人品 100 解锁另一个主题——也就是说“欧皇”由设备决定。

**隐藏主题的线索是倒着写的 URL**：开发者把提示字符串反转，还在代码里用 `Lower("T") + "th"` 拼接来藏 “http”。

**更新标记是一串 800 个星号**：`"EmptyMark****...****"`，用前缀判断“是不是补丁更新”。第一次看到以为是终端输出炸了。

**删除游戏目录要手打 `Potato`**：确认框里的防手滑设计。

## 方法论小结

如果只记一件事，记这个顺序：

```text
先看元数据（是什么、有没有混淆）
→ 找依赖加载方式（单文件怎么装的）
→ 建模块地图（谁大、谁被谁调）
→ 按执行流读（启动/登录/下载三条线）
→ 列能力面 + 追输入来源（安全审计）
→ 用对照实验验证（不要只信代码）
```

反编译只是第一步。真正花时间的是把“这段代码做什么”变成“这个输入从哪来、谁能改、以什么权限执行”。
